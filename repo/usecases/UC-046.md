## Цель
Принять внешнее событие ([[K10]]) так, чтобы каждое было обработано один раз и одним обработчиком, а результат обработки был прослеживаем. Состояния события: `RECEIVED → VALIDATED` или `QUARANTINED → PROCESSED` ([[STATES#external_event]]).

**Два режима** ([[DEC-2026-10-22-04]]):

- **Э1 — ручной.** Адаптера ОИС нет ([[REV-R16]]). «Событие ОИС» — документ ОИС, полученный операционистом в личном кабинете ОИС или по e-mail с УКЭП и зарегистрированный в ЦД ([[DEC-2026-10-22-01]]). Шаги те же, первый выполняет операционист.
- **Цель — API.** Сообщения ОИС принимает интеграционный сервис. У РЦД push-событий нет: событие — изменение, найденное опросом статуса.

**Три класса сообщений ОИС** ([[OD-22]]):

| Класс | Что означает | Меняет учёт? | Аналог ISO 20022 |
|---|---|---|---|
| квитанция | сообщение доставлено | нет | `admi.007` |
| статус | ход исполнения: принято, сопоставлено, ожидает | нет | `sese.024` |
| подтверждение | операция исполнена, с датой и временем — основание для учёта | да, через обработчика | `sese.025` |

## Предусловия
- Профиль обмена задан в CD-D-27: версии форматов, ключи повтора, правила маршрутизации, рубильник квитанций.
- Обработчики выпусков и операций зарегистрированы.

## Основной порядок

### Шаг 1. ОИС передаёт событие
Обязательные поля любого события: источник, ID сообщения, тип, версия формата, ID операции ОИС, номер версии статуса, время у ОИС, наш счёт N, подпись оператора. В Э1 операционист загружает файл документа и вводит эти реквизиты; получение фиксируется в журнале документов [[K21]].

### Шаг 2. Проверка
Подлинность — УКЭП оператора с проверкой сертификата на момент подписи; формат и его версия; целостность (хэш); наличие обязательных полей. Не прошло — карантин `QUARANTINED` (И1, [[R-037]]).

### Шаг 3. Дедупликация и порядок
Три разные проверки ([[R-021]], [[I04]], [[C07]], [[MODEL-Q03]]):

1. **Повтор сообщения.** Ключ — «источник + `eventId`» (в Э1 — регистрационный номер ЦД и хэш файла документа).
    - тот же ключ и то же содержимое — повтор: событие повторно не обрабатывается, возвращается прежний итог (А1);
    - тот же ключ, другое содержимое — конфликт (И2).

    В ручном режиме это ловит «операционист загрузил тот же файл второй раз»: хэш совпал — система показывает уже зарегистрированный документ.

2. **Повтор экономического факта.** Ключ — «ОИС + ID операции ОИС + вид эффекта» ([[C07]]). Ловит одно и то же зачисление, пришедшее двумя разными сообщениями (по e-mail и через личный кабинет; исходное и повторно отправленное ОИС). Второе сообщение сохраняется, но к обработчику не идёт — привязывается к уже проведённой операции.

3. **Порядок версий.** Если по одной операции ОИС приходит несколько статусов («принято» → «исполнено»), они упорядочиваются по номеру версии. Обрабатывается только следующая по номеру; старшая, пришедшая раньше младшей, ждёт (А2); номер меньше уже применённого статус не меняет. У РЦД это `updateNo`.

<details markdown="1"><summary>Ключи и сроки хранения</summary>

| Ключ | Состав | Срок | Повтор с тем же содержимым | С другим содержимым |
|---|---|---|---|---|
| сообщения | источник + `eventId` (Э1 — хэш файла) | бессрочно, вместе с K21 | прежний итог | конфликт ID (И2) |
| эффекта ([[C07]]) | ОИС + ID операции ОИС + вид эффекта | бессрочно | прежняя операция | конфликт и дело |
| запроса (наш к ОИС) | наш `request_key` | бессрочно, не переиспользуется | прежний ответ | отказ |

Основания: прямых норм нет; косвенно — запись не исправляется повтором, только исправительной записью ([[NR-892-1#1.5]]), документ регистрируется один раз под своим номером ([[NR-892-9#1.12]]). У РЦД `receiptId` бессрочный, `updateNo` — порядок, а не ключ. В практике ключ повтора запроса хранится ограниченно (у платёжных API — часы), бизнес-референс операции у депозитариев уникален бессрочно; поэтому здесь все ключи бессрочные.

</details>

### Шаг 4. Передача обработчику
Это не ответ на вызов ОИС и не цепочка внешних сервисов. Внутри ЦД по типу события выбирается **ровно один сценарий**, который выполняет учётную работу:

| Тип события ОИС | Обработчик |
|---|---|
| уведомление об открытии, изменении, закрытии счёта N | [[UC-032]] / [[UC-033]] |
| подтверждение зачисления на счёт N | [[UC-037]] |
| ограничение, арест, его снятие | UC-042–044 |
| выписка по счёту N | [[UC-047]] — срез для сверки |
| неизвестный тип | карантин (И1) |

Технически это внутренний вызов или запись задачи в очередь: шаг только ставит задачу «обработай событие K10 №…». ОИС ответа не ждёт. Учётный результат появляется у обработчика (например, проводка UC-037), а не здесь. Выпуск (UC-027) событием не создаётся — только вручную.

### Шаг 5. Результат и квитанция
- **Само сообщение** — в журнале документов [[K21]]: файл как есть, подпись, хэш, регистрационный номер, дата и время получения ([[NR-892-9#1.12]]). Не меняется никогда.
- **Принятое событие [[K10]]** — ссылка на K21, тип, ID операции ОИС, состояние (`RECEIVED` → `VALIDATED` / `QUARANTINED` → `PROCESSED`) и обработчик.
- **Результат обработки** — у обработчика (операция [[K07]], дело [[K15]]) со ссылкой на K10; в K10 — только ссылка на результат.
- **Техническая квитанция** — ответ «сообщение получено». Подтверждает доставку, а не проводку.
    - **Квитанция ОИС нам** (например, «заявление получено» на заявление UC-032) — сохраняется в K21 как документ и привязывается к нашей операции [[K11]]. Это не исполнение: исполнение — отдельный документ ОИС.
    - **Наша квитанция ОИС** — по рубильнику `send_receipts` в CD-D-27. Включён — квитанция формируется и уходит ОИС после шага 3 (повтор — прежняя квитанция); выключен — не формируется. В Э1 выключен.

## Альтернативные ветви
- **А1, шаг 3. Повтор того же eventId и содержания** → прежний результат, обработчик повторно не вызывается; при включённом рубильнике — прежняя квитанция.
- **А2, шаг 3. Поздняя версия пришла раньше.** Сообщение сохраняется и ждёт предыдущую версию; система ставит задачу «ожидается предыдущая версия» с таймером до конца рабочего дня.

    - **Э1:** запрашивает операционист ЦД тем же каналом, что для заявлений, — личный кабинет ОИС или e-mail с УКЭП: запрос справки о статусе операции с указанием ID операции ОИС. Ответ регистрируется как обычный документ и проходит шаги 2–3.
    - **API:** запрос статуса делает интеграционный сервис по таймеру. У РЦД так работает всё: сервис опрашивает статус поручения по `receiptId` и получает текущий `updateNo`.

    Текущий статус от ОИС закрывает пропуск: промежуточные версии восстанавливать не нужно — важен последний подтверждённый статус.
- **А3, шаг 4. Нет карточки выпуска или счёта.** Пример: пришло уведомление о зачислении выпуска, которого нет среди выпусков ЦД, или на счёт N, к которому выпуск не привязан (UC-033 не выполнен).

    1. Событие K10 и документ K21 сохраняются как есть, состояние — «ожидает сопоставления».
    2. Открывается дело сопоставления ([[K15]]) операционисту: что не найдено и ссылка на документ.
    3. Операционист выясняет причину: выпуск не зарегистрирован — регистрирует ([[UC-027]]); не привязан к счёту N — связывает ([[UC-033]]); ошибка ОИС — пишет ОИС.
    4. Система повторно маршрутизирует **то же** событие с шага 3; нового события нет, повтор эффекта исключён ключом [[C07]].
    5. Карточка выпуска из события автоматически не создаётся ([[REV-R16]]).

    Учёт клиента до этого не меняется. Для зачисления действует срок UC-037: не решено к концу следующего рабочего дня — ЦФА на счёт неустановленных лиц XY ([[REV-R27]]).
- **А4, шаг 5. Обработчик открыл бизнес-кейс.** Пример: зачисление корректное, передано в UC-037, но поручения клиента нет — открыто дело (UC-037 А2).

    - событие **обработано** (`PROCESSED`): передано и принято обработчиком, повторно не маршрутизируется;
    - результат в K10 — «принято в разбор», ссылка на дело K15;
    - квитанция, если включена, означает только «получено», а не «зачислено»;
    - закрытие дела — в обработчике, событие не трогается.

## Ошибки и неопределённые результаты
- **И1, шаг 2. Источник не удостоверен или формат не поддерживается** → карантин, учёт не меняется.
- **И2, шаг 3. Тот же eventId с другим содержанием** → «Конфликт ID», расследование; перезапись запрещена ([[I04]]).
- **И3, шаг 4. Обработчик не ответил** → «Ожидает подтверждения»; перед повтором проверяется результат по ключу эффекта.
- **И4, шаг 5. Квитанция не доставлена** (только при включённом рубильнике) → событие остаётся обработанным, доставка повторяется отдельно.

<details markdown="1"><summary>И1 — что такое карантин</summary>

**Карантин** — состояние события `QUARANTINED`: сообщение сохранено, но к обработчику не передаётся и учёт не меняет. Видно в отдельном списке ЛК ЦД с причиной: подпись не прошла проверку; сертификат не оператора или отозван; формат или версия не поддерживаются; неизвестный тип события; у РЦД — неизвестный код статуса.

**Кто разбирает.** Операционист: запрашивает у ОИС правильный документ (новый документ — новое событие) или признаёт сообщение недействительным. Выпустить из карантина без исправления нельзя.

**Только одно сообщение?** Да — только это. Остальные события обрабатываются дальше, **кроме** более поздних событий **той же операции ОИС**: они ждут, иначе нарушится порядок версий. Если в карантин подряд попадает много сообщений одного типа (например, ОИС сменила формат), поднимается инцидент ([[UC-068]]), а не дело на каждое. Порог — в CD-D-27 (`quarantine_incident_threshold`, например 5 за час).

</details>

<details markdown="1"><summary>И2 — тот же eventId, другое содержание</summary>

Пример: два сообщения с одним ID, в одном количество 100, в другом 120.

- второе сохраняется в K21 как есть, первое не перезаписывается ([[I04]]);
- оба связываются в деле «Конфликт ID»;
- если первое уже передано обработчику, проводка остаётся, дело получает ссылку на неё;
- операционист запрашивает у ОИС, какое сообщение верное;
- если верное второе — исправление делает обработчик по своим правилам (UC-037 А4: исправительная запись в тот же день до отчёта или с согласия депонента, [[REV-R4]]);
- пока дело открыто, новые события этой операции ОИС ждут.

</details>

<details markdown="1"><summary>И3 — обработчик не ответил</summary>

Пример: UC-037 начал проводку, транзакция оборвалась по тайм-ауту.

- событие в состоянии «ожидает подтверждения», сразу повторно не передаётся;
- перед повтором система проверяет по ключу эффекта ([[C07]]), есть ли уже результат у обработчика: есть — событие помечается обработанным с этим результатом, второй проводки нет ([[I12]]); нет — повторная передача тому же обработчику;
- после 3 неудачных повторов (`handler_retry_limit` в CD-D-27) — задача операционисту и инцидент.

</details>

<details markdown="1"><summary>И4 — квитанция не доставлена</summary>

Только при API и включённом рубильнике `send_receipts`.

- событие остаётся обработанным; учёт не меняется и не откатывается;
- отправка квитанции — отдельная задача с повторами: свой счётчик попыток и время последней;
- если ОИС повторно пришлёт то же сообщение — это повтор (А1), в ответ уходит прежняя квитанция.

В Э1 этой ветки нет.

</details>

## Профиль РЦД (цель)
У РЦД нет push-событий: событие — изменение, найденное опросом и подтверждённое запросом статуса; дедупликация по receiptId + updateNo; ответ с меньшим updateNo статус не меняет; неизвестный статус → карантин ([[REV-R16]]). Финальный статус — `COMPLETE`, промежуточный — `DEPOSITING`, отказ — `REJECTED`.
